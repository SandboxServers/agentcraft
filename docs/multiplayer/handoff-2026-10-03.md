## Goal (from the owner)

A fully multiplayer AgentCraft. People join one shared Minecraft world that we host on the colo,
each with their own studio. Each person brings their own AI (a Claude subscription, an API key,
or any other provider) and drives **their own Foreman**. We host **only the Minecraft side**, plus
whatever endpoint the Foremen need to talk to. We never host anyone's agents, code or credentials.

## What upstream is today (verified from the code, not just the README)

- **Foreman** (`foreman/`, Node 22, TypeScript, Claude Agent SDK). Orchestrates agents, one git
  worktree per task, persists state. `src/foreman.ts` is transport-agnostic and has a `Backend`
  interface (`foreman.ts:34`) implemented by `ClaudeBackend` and `SimBackend`. The WebSocket server
  (`src/server.ts`) binds 127.0.0.1:7878 (`AGENTCRAFT_PORT`). It rejects any Origin header and any
  non-loopback Host. It already supports multiple clients (the mod plus CLI tools).
- **Protocol:** `docs/protocol.md`, generated from `foreman/src/protocol.ts` (`npm run gen:protocol-doc`).
  JSON envelope `{v:1,type,id?,...}`. Foreman→mod: snapshot, agent/task/decision/repo/memory/goal
  upserts, agent.log, agent.say, feed.add, diff, notify, status, ack, error. Mod→Foreman: hello,
  goal.submit, user.message, decision.answer, task.action, agent.action, diff.request, repo.add.
- **Mod** (`mod/`, Fabric, **Minecraft 26.3**, Java 25, loader 0.19.5, fabric-api 0.161.0+26.3,
  separate `src/main` and `src/client` source sets).
  - **The Foreman link is in the client**, not the server: `client/foreman/ForemanLink.java`
    (java.net.http WebSocket, auto-reconnect).
  - **Agents are client-only entities** ("architecture A", `mod/DEV.md` §"Agents: client-side
    entities", line ~282). `ClientAgentEntity` has a negative entity id and is `noSave`/`noSummon`.
    `AgentManager` spawns one per Foreman agent in `mc.level` and walks it with `GridPathfinder`
    (A* over client blocks). Server-side mobs (architecture B) were measured and rejected: vanilla
    navigation stops short, jitters, pollutes the save, and players can push the mobs. Keep A.
  - **Server side** (`src/main`): blocks and block entities, the HQ builder
    (`hq/StudioHqBuilder`, `Plan`, `PlanStore`), `layout/Anchors`, `world/HqWorld`, commands.
  - **World changes driven by Foreman state** (lamps, podium, merge station) run through
    `client/world/ServerTasks` and `client/hq/HqWorldDriver` on the **integrated server**, called
    directly from the client. `client/AutoWorld` auto-creates a singleplayer "AgentCraft HQ" world.
    `client/dev/DevCommands` also uses `getSingleplayerServer`. These are the singleplayer
    assumptions to remove.
  - The README states it outright: "Singleplayer, one studio per world, on Minecraft 26.3."
- **Auth today** (`foreman/src/agents/claude/auth.ts`): ANTHROPIC_API_KEY; Bedrock, Vertex,
  Foundry or Claude-on-AWS switches; **`ANTHROPIC_AUTH_TOKEN` + `ANTHROPIC_BASE_URL` (an "API
  gateway") is already detected**, so LiteLLM/OpenRouter-style gateways should work today. The
  claude.ai subscription login is opt-in (`--use-claude-login`) and the code cites Anthropic's rule
  that third parties may not offer claude.ai login. Our design respects that: each person runs
  their own Foreman with their own login, and the server never proxies a login.

## Proposed architecture (v1)

The key idea: **keep architecture A and the "the game is only a view" principle. The server is a
relay and a landlord, not a brain.**

```
Player PC                                              Colo
┌─────────────────────────────┐                        ┌─────────────────────────────────┐
│ Foreman (own repo, own AI,  │                        │ Fabric dedicated server (26.3)  │
│  own compute) :7878 local   │                        │  - studio plots, one per player │
│        ▲ ws, localhost      │                        │  - HQ builder at a plot offset  │
│        ▼ (private: all)     │  Minecraft connection  │  - relays each owner's PUBLIC   │
│ MC client + mod ────────────┼─ custom payloads ─────▶│    state to everyone nearby     │
│  - renders ALL studios'     │  (public subset only)  │  - applies lamp/podium changes  │
│    agents client-side (A)   │◀───────────────────────┤    only to the owner's own plot │
└─────────────────────────────┘                        └─────────────────────────────────┘
```

1. **Foreman stays on the player's PC**, unchanged. It still listens on localhost, and the player's
   own client still connects to it.
2. **The player's client is the bridge.** It forwards a *redacted public subset* of its Foreman
   state to the server over Fabric custom payloads. Identity is free (Minecraft online-mode UUID),
   so v1 needs no separate gateway port, TLS, linking codes or tokens.
3. **The server relays** each owner's public state to the other clients near that studio. Each
   client runs `AgentManager` once per studio, using that studio's anchor layout and namespaced
   negative entity ids, and draws everyone's agents with the existing client-side renderer.
4. **Private data stays local:** code, diffs, decisions and approvals, console, memory library,
   logs. Those screens only ever talk to the viewer's own Foreman. A visitor at someone else's
   podium or merge station sees a read-only summary. This makes forged approvals impossible by
   construction.
5. **Block changes move server-side:** `ServerTasks`/`HqWorldDriver` become C2S packets ("set my
   studio's lamp X to Y"), validated on the server as "sender owns this plot".
6. **When the owner logs off,** their studio shows its agents as asleep or offline (AgentManager
   already has a "Foreman offline" dimmed state), or hides them.

**Later option (v2): a direct Foreman→server gateway.** It would let a studio stay live while its
owner is out of the game. That needs an outbound wss connection from Foreman, a `/agentcraft link`
one-time code to bind it to a UUID, server-issued tokens, and TLS on the colo. Don't build it
until v1 works.

### Redaction policy (needs an owner decision; proposed default)

The default public fields are agent identity and skin, status, station or activity *category*,
and progress counts. Off by default, opt-in per studio: speech bubbles (`agent.say`), task titles,
goal text, activity detail strings. These can leak file names, code or private plans. Define this
as an explicit allowlist in one place, with a test.

### Bring-your-own provider

- Works today: `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN` gateways, the cloud switches, an API
  key, or the player's own `--use-claude-login`.
- Later: more `Backend` implementations (for example, wrapping Codex CLI or Gemini CLI). The
  interface at `foreman.ts:34` is the seam. Check how much of `ClaudeBackend` (stream parsing,
  tools, cost tracking, `agents/claude/*`) is Claude-specific before promising this.

## What the colo hosts

- One Docker container: Fabric dedicated server for 26.3, Java 25, about 2–4 GB of RAM,
  `online-mode=true`, whitelist on, port 25565 open. No agent code, repos or API keys.
- Access: SSH via the owner's private host alias (never written in this public repo) (passwordless sudo, docker group). **This fork is public: never commit
  the colo's address, hostnames or credentials.**
- The Cimmeria emulator also runs there. Check RAM and CPU headroom before sizing, and keep the
  two separate (own compose project, own ports).
- Players need the mod jar (and Fabric API) on a 26.3 Fabric client. Plan a modpack or launcher
  profile later.

## Plan

0. **Spike (read-only, first).** Set up the toolchain (Java 25, Node 22, `cd foreman && npm ci &&
   npm run check`, `cd mod && gradlew build`). Then answer:
   - Does the mod jar load on a **dedicated** server today (`gradlew runServer`)? List every
     `src/main` → client dependency and every `getSingleplayerServer` call.
   - Where do the HQ plan and anchors live (`PlanStore`), and can they be offset per plot?
   - Which protocol fields would the public subset need for `AgentManager`/`StationAssigner` to
     animate a remote studio correctly?
   - Write the findings and a phased plan to `docs/multiplayer/` and get owner sign-off.
1. Dedicated-server boot: AutoWorld and singleplayer paths become no-ops when connected to a remote
   server. A plot allocator places one studio per player on first join.
2. Public-state relay: the payload types, the redaction allowlist, per-studio `AgentManager`,
   namespaced entity ids. Test with two clients on one machine (sim backend, two Foremen on
   different `AGENTCRAFT_PORT`s).
3. Server-side block changes with ownership checks. Visitor read-only screens.
4. Colo deployment (compose, whitelist, backups of the world), plus player install instructions.
5. Optional: v2 gateway, extra provider backends.

Keep multiplayer behind a mode, or confined to new classes where possible, so merging upstream
stays cheap (upstream is active: PR #1 for macOS landed recently). Consider asking upstream
whether they'd want multiplayer contributed back.
