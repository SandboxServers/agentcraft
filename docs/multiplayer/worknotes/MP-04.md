## APIs and implementation details for later packets

- **Dirty tracking:** Clients and singleplayer integrated servers never set `dirtyTrackingActive`, so `dev.mp.fake` and remote layout applies do not grow `DIRTY`.
- **Republish:** `SEND_REMOVAL` when the studio id is absent from `Anchors.all()` (server unpublish). `NOTHING` when the studio is `LOCAL`, has no plot in `Plots.directory()`, or holds an empty layout snapshot. `publishStudio` only fans out to `StudioRange.viewersOf`.
- **Drain:** Each server tick takes one batch; studios dirtied during fan-out remain for the next tick.

## Pull-request review

One reviewer comment on `LayoutSyncClient.remove`, checked against the code and found valid.

- **Cause:** `Anchors.remove` notifies the studio listeners; the one `Studios.init` registers runs `Studios.remove` through the Minecraft executor, which runs a task inline when the caller is already on the client thread. `LayoutSyncClient.remove` then called `Studios.remove` again, and `Studios.remove` notifies its listeners even when the studio is already gone, so every `LayoutRemoveS2C` produced two removal notifications.
- **Fix:** `LayoutSyncClient.remove` no longer calls `Studios.remove`. `Anchors.remove` is the single removal path; the foundation files are unchanged.
- **Timing:** unchanged. The receiver runs `remove` on the client thread, so the view and the plot are gone before `Anchors.remove` returns. Nothing in this packet reads the registry after the removal (`layout_removed` logs only ids).
- **Dependency:** the removal of the view and the plot now relies on the `Studios.init` listener. `ClientFeatures` calls `Studios.init`, and `WiringTest` checks that call is there.
- **Tests:** `LayoutSyncClientTest` has five tests (was four). The new `remove_notifies_studio_listeners_exactly_once` registers the `Studios.init` listener, applies one layout and one removal, and expects one removal notification; it fails on the old code with two. `remove_clears_layout_plot_view_and_logs_removed` now registers the same listener, since the plot is cleared through it. `Studios.init` itself cannot run in JUnit: its listener calls `Minecraft.getInstance()`, which is null without a running client, and `Anchors` has no way to drop a listener. The tests call the method that listener calls, `Studios.anchorsChanged`, with `Runnable::run` as the executor.
- **Verification:** `gw build -x runGameTest`: 55 tests, 0 failures, 0 skipped (the foundation's 46 and MP-04's 9; the Verification table above records the 54 before this round). `game gw-raw build`: BUILD SUCCESSFUL, "All 2 required tests passed".
