## Decisions and details to build on

- **The remote agent card goes through the foundation seam.** `VisitorFeature.init()` calls
  `RemoteAgentClicks.set((studio, agentId) -> ...)`. MP-08 owns the click and must call
  `RemoteAgentClicks.fire(studio, agentId)` for an agent in a studio whose `StudioView.own()` is
  false; it must not open `AgentCardScreen` itself. With MP-08 absent (this branch), the seam is
  exercised by `dev.visitor.agent`.
- **The gate only sees blocks that already have a handler.** `StationInteractions` consults the gate
  after the `HANDLERS.get(...)` lookup, so the gate can map the clicked block to a station token.
  Monitors, status lamps and the atrium have no `onUse` handler and are not clickable stations.
- **The closed station set** is `VisitorGate.Station`: `podium`, `merge`, `task_wall`, `archive`,
  `catalog`, `lectern`, `console`, `agent` for the card, and `station` for the generic fail-closed
  case. The tokens are the telemetry `station` value and the `dev.visitor.use` argument. (The
  work-packets Decision calls this "a closed set of constants in the packet's own feature class";
  the set lives in the packet's own `client/mp/visitor/` package, not in
  `MpEvents`/`MpReasons`.)
- **The gate fails closed.** `VisitorGate.visitorKind(studio, mapped)` returns empty only for
  today's handler (own studio or no studio). For a remote studio it returns the mapped station, or
  `station` when the block is not in the map, so a remote block that already has a handler is always
  consumed and can never reach a local feature handler with the remote studio's context.
- **The remote agent card is live.** `AgentCardScreen` keeps the `StudioId` and the agent id, not a
  snapshot. Each frame it resolves `Studios.view(id)` and `VisitorGate.findAgent(view, agentId)`
  against the view's current `publicState`, draws that, and closes when the view, its state or the
  agent is gone. `dev.visitor.agent` still checks the lookup before opening, so a missing agent does
  nothing.
- **Telemetry.** `VisitorGate.logOpen(Route, Station, StudioView, UUID)` emits
  `visitor_readonly` only for `Route.VISITOR`; the overload without the route always logs. Fields:
  `player` (viewer UUID), `studio` (owner UUID), `plot` (`-1` when the client has no plot for the
  studio, which is the overlay case until MP-04 syncs a plot), `rev` (`-1` when no state), `station`
  (closed token), `action` (`open`). No owner name, activity, task, goal or address ever reaches the
  line.
- **Public copy only.** The station panel shows `Counts` and fixed privacy lines; the task-wall
  titles are gated on `policy.taskTitles()` and `tasks != null` (the record refuses tasks otherwise).
  Goal text is never shown by a station panel. The agent card shows state, station and awaiting; it
  deliberately stays minimal per the packet text (name, state, station, awaiting) and never reads
  `activity`.
- **The gate gates block clicks, not keybinds.** The console key (`` ` ``) and the decisions key
  (`J`) are untouched and still talk to the viewer's own Foreman anywhere in the world.
- **DevBridge.**
  - `dev.visitor.use {station, studio?}` — resolves the first non-own studio (or a UUID), checks
    `Route.VISITOR`, logs and opens `VisitorStationScreen`, and returns `{screen, visitor, station,
    studio, ownerName, online, plot, rev, lines}`. The token may be any of the closed set, including
    the generic `station`.
  - `dev.visitor.click {x,y,z}` — runs the real `UseBlockCallback.EVENT.invoker()` at a block
    position, so it exercises the installed gate and the exact callback a right-click uses, then
    returns `{pos, result, screen, studio, own, station?}`. `x`, `y` and `z` are **required**
    integers (a request without one is refused, not read as 0). With the overlay on the result is
    `FAIL` and the screen is `VisitorStationScreen`; with it off the real station screen opens.
  - `dev.visitor.agent {agent, studio?}` — fires `RemoteAgentClicks.fire(studio, agentId)` (the call
    MP-08 will make) and returns `{screen, agent, visitor, input, studio}`.
  - `dev.screen {open:"visitor"}` — shows a panel for the first remote studio (the overlay).

## Open risks

- **Fail-open before a remote layout syncs.** `VisitorGate.route` follows the campaign's renderer
  rule: `Studios.at(pos)` empty means today's handler. In multiplayer, before MP-04 delivers a
  remote studio's plot/layout, a click in that area could reach the viewer's own handler. This is
  the contract-mandated path, closed in MP-I and server-side by MP-13; it is deliberately not
  worked around here.
- **Enter while looking at a terminal** (`ConsoleFeature`) opens the local console directly, not
  through `StationInteractions`, so it is not gated. It passes no block or binding, so it never
  submits a remote studio as context; the packet only requires the console key to keep working, and
  the cursor-plan Q3 recommendation is to leave Enter as it is. See the contract change request.
- **The overlay has no registered plot**, so `dev.visitor.*` reports `plot=-1`; real multiplayer
  (`StudioStateS2C` after MP-04) fills it.
- **Remote agent lookup by id.** `openAgentCard` checks `VisitorGate.findAgent` before opening, and
  the card re-resolves the same lookup every frame; if the state is missing the id (an unusual
  overlay fixture) nothing opens, and if the id later leaves the state the card closes. It never
  falls back to the viewer's own `AgentManager`.

## Pull-request review

One comment from the automated reviewer, checked against the code and found valid: the task-wall
panel could grow past the screen.

- **The numbers.** `PublicJson.fromJson` accepts up to 32 public tasks, so `VisitorGate.stationLines`
  returns up to 34 rows for the task wall. At 10 px a row the panel was 411 px high (71 px of
  padding, header and footer). A 960x540 window resolves to GUI scale 2, a 480x270 screen: the last
  12 task rows and the footer were below it. The 1920x1080 dev window at scale 3 (640x360) was too
  short as well.
- **The change.** `VisitorGate` has three pure helpers: `rowsAvailable(height, chrome, rowHeight)`,
  `fit(total, available)` returning `Fit(shown, remaining, indicator)`, and `moreLine(remaining)`.
  `VisitorStationScreen.layout()` keeps a 4 px margin above and below the panel and sizes it from
  the fitted rows; the body draws the first `shown` lines and, when truncated, a last muted row
  "+ N more" (a count only). The header and the footer are always drawn, and a body that fits is laid
  out exactly as before. On the 480x270 screen a full task wall shows 18 rows and "+ 16 more" in a
  261 px panel. A screen shorter than the 71 px fixed part plus the margins gets no body row; the
  fixed part is not shrunk. The dev commands' `lines` field still returns every public line.
- **Tests.** Three new JUnit tests in `VisitorGateTest` (nine in the class): a 32-task wall gives 34
  rows and is cut to 18 plus the indicator with 16 remaining; a body that fits is shown whole with no
  indicator; a screen too short for a row gives no row and never a negative count. With `fit`
  returning every row (the old behaviour) all three fail. `gw build -x runGameTest`: **55 JUnit
  tests, 0 failures, 0 errors, 0 skipped**.
- **Owed in game:** a fake remote studio with `taskTitles` on and 32 tasks, the task-wall panel in a
  960x540 window, and the screenshot read: header, 18 rows, "+ 16 more" and footer inside the screen.
