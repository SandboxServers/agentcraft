## Minecraft and Fabric API notes (checked, not remembered)

Every signature below was read in the read-only decompiled 26.3 sources under `<repo>/mod/build/mcsrc` or with `javap` against the cached Fabric jars. No source generation ran.

- `MinecraftServer.isDedicatedServer()` (`MinecraftServer.java:1326`, abstract; `DedicatedServer.java:438`), `overworld()` (`:1171`), `getGameRules()` (`:2117`).
- `GameRules.get(GameRule<T>)` / `set(GameRule<T>, T, @Nullable MinecraftServer)` (`world/level/gamerules/GameRules.java:120,129`). `LOG_ADMIN_COMMANDS` is a `GameRule<Boolean>` (`:46`), `MAX_BLOCK_MODIFICATIONS` a `GameRule<Integer>` (`:47`). 26.3 uses the typed `GameRule` registry, not 1.21's boolean `RULE_*` fields.
- `ServerPlayer.gameMode()` (`server/level/ServerPlayer.java:1807`) and `boolean setGameMode(GameType)` (`:1782`, returns false without changing the mode if it could not apply). `GameType.getName()` is lower case (`world/level/GameType.java:51`).
- `ServerLevel.getChunkSource()` (`server/level/ServerLevel.java:1207`) → `ServerChunkCache.getGenerator()` (`:435`) → `ChunkGenerator`. `FlatLevelSource.settings()` (`world/level/levelgen/FlatLevelSource.java:57`) → `FlatLevelGeneratorSettings.getLayers(): List<BlockState>`, expanded bottom-up (`world/level/levelgen/flat/FlatLevelGeneratorSettings.java:190`). Top y = `height.getMinY() + layers.size() - 1`, so a non-flat or wrongly-layered world is detected without loading chunks or probing blocks (`Level.getHeight` returns `getMinY()` when the chunk is not loaded — not usable here).
- Fabric `FabricLoader.getLaunchArguments(boolean)` (`fabric-loader 0.19.5`, `net.fabricmc.loader.api.FabricLoader`). Verified by `javap` that the implementation removes the *value* that follows a sensitive option (`MinecraftGameProvider.SENSITIVE_ARGS`, which includes `username`, `password`, `session`, `accesstoken`, …); `--quickPlayMultiplayer` is not sensitive, so its value arrives intact. The value is only used to test non-blankness and is never logged.
- Vanilla parses `--quickPlayMultiplayer` as an option with a required argument (`client/main/Main.java:88-92`) and quick play can connect without a title screen (`client/quickplay/QuickPlay.java:42-50,96-108`, which builds a `JoinMultiplayerScreen` parent). Hence the parser accepts a following token or `=` and rejects a bare option.
- `Gui.screen()` (`client/gui/Gui.java:230`) is the 26.3 current-screen accessor; a multiplayer screen is `client/gui/screens/multiplayer/JoinMultiplayerScreen` or `client/gui/screens/ConnectScreen`, not `MultiPlayerGameMode`.
- The game-test helpers used: `GameTestHelper.getLevel()`, `assertTrue/assertFalse/assertValueEqual/fail` (`gametest/framework/GameTestHelper.java`), and `net.fabricmc.fabric.api.entity.FakePlayer.get(ServerLevel)` (`fabric-events-interaction-v0`). `FakePlayer`'s constructor installs a no-op `ServerGamePacketListenerImpl`, so `setGameMode` does not touch the network.

## Seams and decisions another packet needs

- `HqWorld.multiplayer(MinecraftServer)` is the one predicate for "multiplayer active"; MP-03 and later should reuse it rather than re-reading `isDedicatedServer && enabled` themselves.
- `HqWorld.applyServerRules(MinecraftServer)` and `HqWorld.onPlayerJoin(MinecraftServer, ServerPlayer)` are public test seams; production is the registered listeners.
- `ServerWorldFeature.checkSurface(MinecraftServer)` and `surfaceProblem(...)` are public for tests. The check is startup-only and installs nothing, so `MpServerConfig.install` never re-runs it (the game-test world, enabled=false at boot, is unaffected).
- `world_rules_applied`'s `rules` field is the **count of rules written** (19). The coordinator approved the `config_invalid` surface shape; it carries the frozen `key`/`value` plus `reason=surface_not_64`. See "Contract change requests".

## Deviations

- `AutoWorld` gets the `disabled` reason from the `AGENTCRAFT_AUTOWORLD=0` env switch. With `disabled` env=off, the process was normally not launched with quick play; checking the flag first would be crisper, but two checks is not worth the complexity, so the env switch is reported first.
- `isHq` now returns false whenever multiplayer is active, whatever the level name. This is the packet's explicit rule and is what stops an enabled server from building a `LOCAL` studio at the origin. The two other `isHq` callers (`Anchors`, `HqFeature`) are untouched.
- `firstStart` is skipped entirely when `worldRules:false` on a first multiplayer world (the marker is not written, so an operator who later turns rules on still gets the initial time/weather). The packet says only "`worldRules:false` changes nothing"; this is stricter, and does not touch singleplayer.

## Open risks

- **Undecompiled assumption to watch:** `FlatLevelGeneratorSettings.getLayers()` is flat-expanded (one `BlockState` per y). The game-test world's sandstone top at y=3 confirmed the arithmetic empirically. The live grass-at-64 check is deferred to the coordinator (below).
- The superflat requirement is not enforced for `enabled:false` servers, which is the intended rollback lever; MP-14's deployment config must ship the flat world.
- `FabricLoader.getLaunchArguments` on a launcher that hides its arguments returns an empty array, so the quick-play skip falls back to the screen guard. The screen guard is what makes the skip reliable; the arg check is an early, cheap path.

How the refusal looks to an operator: Minecraft prints `Done (…)!` first, because Fabric raises `SERVER_STARTED` after it. The check then throws, Minecraft writes a crash report naming the reason (`AgentCraft multiplayer requires a superflat world with grass at y=64 (found not_flat)`) and stops before the first tick, so nobody can join. **The process exits with status 0.** A container with a restart policy will therefore start it again and fail the same way each time; MP-14's documentation should say so.
