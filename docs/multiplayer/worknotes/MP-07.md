## API notes for later packets

- `HqWorldDriver.compute(ForemanState) → Wanted` is the full state (what singleplayer applies). `HqWorldDriver.compute(ForemanState, Anchors.Layout) → WorldIntent` is the wire snapshot: the full state through the pure filter `wireIntent`. `layout` is reserved for future use; lamp colours come only from `ForemanState`.
- `HqWorldDriver.wanted()` returns a stored `Wanted` (not rebuilt per call), as of the last recompute: the full state while the driver is not sending, and the state derived from the filtered intent while it sends to a server (what that server will show). `HqClientFeature` reads it for `dev.state.hq`.
- `WorldIntentFeature.handle(MinecraftServer, UUID, WorldIntent)` is the server entry point (gate, plot resolution, rate limit, apply, telemetry). `setClock`, `resetPlayer` and `resetState` are the test seams.
- `IntentApplier.apply(ServerLevel, Plot, StudioId, WorldIntent, Set<Integer>)` applies inside the plot box; the set holds plot indexes that already logged an unknown binding server-wide.
- **Trust boundary:** only `player.getUUID()` → `Plots.directory()` and server-side block-entity bindings decide what changes. No payload position or studio id is used.
- **Singleplayer:** `tick(Minecraft)` passes an `Applier` that calls `ServerTasks.run`, so the world writes happen on the integrated server thread exactly as on the base, with the full `Wanted` (`ci:<repoId>`, every repo slot, every agent). **Multiplayer:** the driver sends the filtered `WorldIntentC2S` only (no local apply). **REMOTE_VANILLA / closed channel:** nothing is sent.
- `DecisionsFeature.syncPodium` is the only writer of the podium override; there is no pending map, and the override takes effect on the next driver tick without waiting for a Foreman revision. The renderer repeats its wish every frame: `setPodiumOverride` ignores a wish that agrees with the podium state the driver last applied while no override is set, so a quiet studio does not recompute every tick.
- No client-side `agentcraft.mp` event. All telemetry is server-side.

## Pull-request review

The review found that `HqWorldDriver.compute` put no bound on agent lamps or lit monitors, while the wire accepts at most 64 lamp keys and 64 lit monitors (`PublicJson.intentFromJson`), so a Foreman with many agents would build an intent the codec refuses and, once the `WorldIntent` constructor enforces the same caps, would throw out of the client tick. The wire intent now takes both caps from `MAX_LAMPS` and `MAX_LIT_MONITORS`: the CI lamps and the five fixed keys always go in, and agent lamps and lit monitors are added in the Foreman's order until a cap is reached. The caps apply to the intent sent to a server only; singleplayer applies the full state without them (see the owner ruling below; the first version of this fix capped singleplayer as well). The two caps are independent: on the server an agent past the lamp cap has no lamp entry and its lamp goes dark; an agent past the monitor cap has no monitor entry and its monitor is unlit. The fixed and CI keys take lamp places, so with one repository agents 59 to 64 have a dark lamp and a lit monitor on the server. `WorldIntentComputeTest.aHundredActiveAgentsStayInsideTheWireCaps` covers it with 100 injected agents (64 lamps, 64 lit monitors, fixed and CI keys present, the first agents kept and the last left out, round-trip through `PublicJson`), and the two reference comparisons pass unchanged.

## Owner ruling 2026-10-04: singleplayer restored

The owner ruled on the pull request that singleplayer stays unchanged and that only what is sent to a server is filtered; the `ci:<repoId>` lamp binding is a documented feature (`mod/FEATURES.md`). Before this change the driver built one wire-safe `WorldIntent` and used it on both paths, so singleplayer had lost, compared with the base: the `ci:<repoId>` lamp key, `ci:#<n>` past the eighth repo, the lamp and lit monitor of an agent whose id is not a legal wire binding, and every agent past 64 lamps or 64 lit monitors.

`HqWorldDriver` now has the base's `compute(ForemanState)` back, returning the full `Wanted`, and a pure filter `wireIntent(Wanted, agentOrder, revision)` that turns it into the `WorldIntent`. `compute(ForemanState, Layout)` is the first through the second and returns what it returned before. In `tick` the `Applier` receives the full `Wanted` and the pacer is offered the filtered intent; "content differs" is decided separately for the two, so a change the wire does not carry applies locally and sends nothing. The podium override is resolved once per tick and lands in both. `wanted()` reports the full state while not sending and the filtered state while sending. No server-side file changed (`IntentApplier`, `WorldIntent` and the codec are as they were).

The shape of `monitorLit` is the base's again on the local path (`id -> isActive()` for every agent; the intent-derived `Wanted` has entries for lit monitors only). That difference was not observable: the applier treats a missing entry and `false` alike, and `dev.state.hq` does not list monitors.

One theoretical difference remains between the filter and the previous wire `compute`: a repo whose id is literally `#<n>` shares its `ci:<repoId>` key with a slot key, and the filter then sends what singleplayer shows for that key. The Foreman derives repo ids from a slug of the directory name, which cannot contain `#`.

Tests: six new JUnit tests (two in the golden compare of the full `Wanted` with the reference, one for the filter on a hand-built `Wanted`, three through the `tick` seam with 12 repos, a 17-character agent id, an off-shift agent and 100 more agents). The five that test the restoration failed on the previous code. `gw test --tests 'dev.agentcraft.client.hq.*'` passes with 26 tests (11 + 15), 0 failures, errors or skips. The full build, the game tests and the singleplayer QA compare have not been rerun on this revision; the test counts in the status line and the verification table above are from earlier revisions.
