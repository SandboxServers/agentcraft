## API notes for later packets

- `HqWorldDriver.compute(ForemanState, Anchors.Layout) → WorldIntent` is the pure snapshot. `layout` is reserved for future use; lamp colours come only from `ForemanState`.
- `HqWorldDriver.wanted()` returns the `Wanted` that was applied last (stored, not rebuilt); `HqClientFeature` reads it for `dev.state.hq`.
- `WorldIntentFeature.handle(MinecraftServer, UUID, WorldIntent)` is the server entry point (gate, plot resolution, rate limit, apply, telemetry). `setClock`, `resetPlayer` and `resetState` are the test seams.
- `IntentApplier.apply(ServerLevel, Plot, StudioId, WorldIntent, Set<Integer>)` applies inside the plot box; the set holds plot indexes that already logged an unknown binding server-wide.
- **Trust boundary:** only `player.getUUID()` → `Plots.directory()` and server-side block-entity bindings decide what changes. No payload position or studio id is used.
- **Singleplayer:** `tick(Minecraft)` passes an `Applier` that calls `ServerTasks.run`, so the world writes happen on the integrated server thread exactly as on the base. **Multiplayer:** the driver sends `WorldIntentC2S` only (no local apply). **REMOTE_VANILLA / closed channel:** nothing is sent.
- `DecisionsFeature.syncPodium` is the only writer of the podium override; there is no pending map, and the override takes effect on the next driver tick without waiting for a Foreman revision. The renderer repeats its wish every frame: `setPodiumOverride` ignores a wish that agrees with the podium state the driver last applied while no override is set, so a quiet studio does not recompute every tick.
- No client-side `agentcraft.mp` event. All telemetry is server-side.

## Pull-request review

The review found that `HqWorldDriver.compute` put no bound on agent lamps or lit monitors, while the wire accepts at most 64 lamp keys and 64 lit monitors (`PublicJson.intentFromJson`), so a Foreman with many agents would build an intent the codec refuses and, once the `WorldIntent` constructor enforces the same caps, would throw out of the client tick. `compute` now takes both caps from `MAX_LAMPS` and `MAX_LIT_MONITORS`: the CI lamps and the five fixed keys always go in, and agent lamps and lit monitors are added in the Foreman's order until a cap is reached, in singleplayer as well as in multiplayer. The two caps are independent: an agent past the lamp cap has no lamp entry and its lamp goes dark; an agent past the monitor cap has no monitor entry and its monitor is unlit. The fixed and CI keys take lamp places, so with one repository agents 59 to 64 have a dark lamp and a lit monitor. `WorldIntentComputeTest.aHundredActiveAgentsStayInsideTheWireCaps` covers it with 100 injected agents (64 lamps, 64 lit monitors, fixed and CI keys present, the first agents kept and the last left out, round-trip through `PublicJson`), and the two reference comparisons pass unchanged.
