## APIs and implementation details for later packets

- **`StudioRelay` seams.** `SendSink` (`sendState`/`sendPresence`/`sendEvent`, each returning whether the payload was sent), `ViewerSource` (`viewersOf(StudioId)`) and `OnlineSource` (`online(UUID)`) are the only ways payloads leave, viewers are found or connectivity is read. Production is in `RelayFeature`; JUnit provides a recording sink, a fixed viewer list and a fixed answer. `acceptState`/`acceptEvent` take the sender UUID, directory, config, equipped flag and an explicit `nowNanos`.
- **`StateResult`** is `ACCEPTED`, `UNCHANGED`, `NO_PLOT`, `BAD_VERSION`, `RATE_LIMITED`. `acceptAndRelayState` relays only on `ACCEPTED` and re-stores an `UNCHANGED` state so its newest `rev` is kept. `EventResult` is `ACCEPTED`, `NO_PLOT`, `BAD_VERSION`, `RATE_LIMITED`, `UNKNOWN_AGENT`.
- **Change detection** compares every content field except `rev` (`sameContent`), so a republished identical state keeps the newest `rev` but is not fanned out again.
- **Rate buckets** hold a `RateBucket`, its rate and its last use; if the current config's `publicStatePerSecond` differs from the stored rate, the bucket is rebuilt. The rate is kept beside the bucket (`Limited.rate`), so the foundation class was not edited. See "Pull-request review" for when a token is taken and how long a bucket lives.
- **Presence truth** is whatever the `OnlineSource` reports. Production reads `server.getPlayerList().getPlayer(owner) != null`; `StudioRelay` keeps no online cache. `onEntered` sends presence plus the retained state (online or not), skipping the owner.
- **Privacy:** telemetry carries counts, UUIDs, plot indexes, revs, booleans and `MpReasons` constants only. `Say.text` and opt-in activity/goal/task text never reach `MpLog`.
- **Threading:** the server receivers mutate directly, because Fabric calls a play receiver on the server thread (see "Pull-request review"); `JOIN`/`DISCONNECT` hop with `srv.execute`; client mutations run in `context.client().execute`. `StudioRange.Listener.entered` is invoked on the server thread.

- **`player.getGameProfile().name()`** is the 26.3 record accessor (verified with `javap` against `authlib-10.0.77.jar`). It is the plain profile name, which is what `PresenceS2C.ownerName` carries.
- **`bytes`** is the UTF-8 length of the outbound payload JSON, excluding Minecraft framing and the payload identifier.
- **`recipients`** counts only the sends the sink accepted (a viewer that `canSend` refuses is not counted).

## Pull-request review

A human review of the pull request raised two findings. Each was checked against the code, the Fabric networking jar and the 26.3 sources before anything changed.

- **Bucket first (finding 1, valid).** `acceptState` and `acceptEvent` take a token from the sender's bucket before any other check, so a sender with no hello or no plot is limited too and is refused `rate_limited` once it runs out; that line carries `plot=-1` for a sender without a plot, as `relay_sent` and `presence` do. Buckets are per player UUID, states and events separate, and survive a disconnect. A bucket unused for five seconds is dropped when another is created (it is full again after two seconds, so a new one is no different), and all go at server stop, so a map never holds more than the senders of one five-second window plus the newest.
- **Refusal lines are throttled (finding 1, valid).** At most one line per player, event and reason every five seconds (`WINDOW_NANOS`, on the `nowNanos` argument). No line changed, and a refusal never depends on the throttle. Expired entries are dropped when a new key is added.
- **No second hop (finding 1, valid).** Fabric's `AbstractChanneledNetworkAddon.handle` throws `RunningOnDifferentThreadException` unless `ServerPlayNetworkAddon.isOnReceiveThread()` (`server.packetProcessor().isSameThread()`), and its mixin then queues the packet on the `PacketProcessor`, which the server thread drains. A play receiver therefore always runs on the server thread, and the two receivers call the relay directly.
- **Freed plots (finding 2, partly fixed).** `StudioRelay` looks a plot up in one helper only (`owned`), which drops the stored state of a studio that has none. Every state and event accept calls it on every path, before any refusal is decided and whether or not a refusal line is logged, so a `rate_limited` or `bad_version` packet after a free drops the state too (the security re-review found the `rate_limited` paths skipping it); so do the state relay, the event relay, range entry, join and disconnect. Range entry then sends nothing. The name is kept while its owner is connected, because it is recorded only at join and a plot may be allocated later in the session; it still goes at a disconnect without a plot. **Left for MP-I:** a plot freed and allocated again with none of those calls in between keeps its old state, so the plots packet's free hook must drop the studio's state and name.
- **`Say.to` (finding 2, valid).** The contract allows an agent id or `"user"`; the relay sends any other value as absent. MP-05's publisher also sends the Foreman's `"all"`, which now arrives as absent; the client draws both the same way.
- **Tests.** Seven new JUnit tests (101 in all): a sender with no plot or no hello is refused for that up to its bucket's capacity and `rate_limited` after it; 1,000 refused states in one second log two lines, a second sender logs its own, and the reason is logged again after five seconds; the bucket survives a reconnect and idle entries are dropped; a freed plot's state is dropped and not served again, also when the packet after the free is `rate_limited` (state and event, line logged or throttled) and on an event relay; `to` is narrowed. Each was shown to fail with its guard removed. No existing expectation changed.
