### The smoke test

Boot 1 with the shipped config: the entrypoint logs `Seeded config/agentcraft-server.json.`, the server logs `event=config_loaded enabled=false file=config/agentcraft-server.json` and no `event=config_invalid`, the studio builds, `setblock` works and `backup.sh` runs. Boot 2 on the same volume and shipped config is the Watchtower restart: the placed gold block survives and `Loaded layout` appears. Boot 3 mounts an `enabled: true` copy at `/data/config/agentcraft-server.json` and checks `event=config_loaded enabled=true file=config/agentcraft-server.json` and, once MP-03 is in the jar, that `/help agentcraft` lists the `plot` sub-command. The image also has its shipped default read directly out of `/opt/agentcraft/defaults/config/agentcraft-server.json` and required to be `"enabled": false`.

Boot 2 deliberately stays on the shipped (`enabled: false`) config: with MP-01 in the jar, `enabled: true` makes `HqWorld.isHq` false, so `Anchors`' `LOCAL` load does not run and `Loaded layout` would not appear. The enabled check is therefore its own third boot.

## Deviations, notes and open risks

- **Nothing was built or run for the image.** The Dockerfile change, the entrypoint seed of the new file and the smoke step are checked only by reading, YAML parsing and `sh -n`. The release workflow's own run is the first real execution. A manual dispatch publishes `latest-prerelease`, so the owner should run it at close-out (or smoke in a throwaway project on the colo).
- **The plot check is `rcon_says "help agentcraft" 'plot'`,** not a `plot list` output match: MP-03 is a parallel packet and its exact `list` text is not in this branch. `/help agentcraft` goes through Brigadier's `getSmartUsage`, so a registered `plot` literal appears in the response regardless of its own output. It fails a release cut before MP-03 merges, as intended and as the Decision says.
- **The enabled path is a mounted file** (`-v …:/data/config/agentcraft-server.json:ro`) rather than a write into the named volume. Both are equivalent; the mount matches the Decision's wording and keeps the shipped seed's own boot untouched.
- **`world_rules_applied` is asserted on the enabled boot** (added by the coordinator at review: MP-01 is in the integration branch). Together with the plot check this means a release cut before MP-01 and MP-03 are on `main` fails the third boot by design: merge MP-14 to `main` after both.
- **`logs_lack 'event=config_invalid'`** catches a typo'd or unknown key in the shipped seed, which `enabled=false` alone would not (a misspelled boolean falls back to `false` silently).
- **No `smoke_only` workflow input was added.** The advisor plans proposed one; the Decisions did not adopt it, so a dispatch still publishes. It is listed under "Contract change requests" rather than added here.
- The world requirement (superflat, grass at y = 64) is stated in `deploy/server/server.properties`, `docs/multiplayer/deploy.md` and the config's documentation. The JSON itself carries no comment because MP-F's loader logs `config_invalid` for unknown keys.
